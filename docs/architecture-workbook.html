STEP 01 done

The mental model

No-jargon version: a hospital's records are private and don't play well with anyone else's. This is the plain-English path they take to become an answer to "who qualifies for this trial?" Each step below is one short paragraph — open "Technical details" only if you're curious what it's actually built with.

Two terms people mix up FHIR is the shipping label — it makes sure one patient's record can be read the same way no matter which hospital's software wrote it. OMOP is the warehouse layout — it reorganizes thousands of patients' records into one consistent structure so you can count and compare across every hospital at once. You need both, and they do different jobs — one isn't just a fancier version of the other.

0

The hospital's own system

This is just the hospital's private database — a diagnosis, a lab result, a prescription, stored however that hospital's software happens to store it. Nobody outside can read it directly, the same way you can't open someone else's private spreadsheet over the internet.

Technical details
Lives in the EHR (e.g. Epic, Cerner), tied to a local patient ID (MRN). Proprietary schema, not exposed for outside analytics.
1

Published in a standard format

The hospital's system translates that private record into FHIR — a standard format for health data, similar to how a PDF looks the same on any computer no matter which program made it. The diagnosis, the lab result, and the prescription each become their own clearly labeled piece of data that anyone with permission can read the same way.

Technical details
FHIR resources produced: Patient, Condition (the diabetes diagnosis), Observation (the HbA1c result), MedicationStatement (Metformin), Encounter. Older hospital systems may still use HL7 v2, an older messaging format — nobody queries it directly, it's usually converted to FHIR first.
2

A permanent, untouched copy

Before changing anything, we save an exact copy of what the hospital sent, forever. If we later discover a mistake in how we processed the data, we redo it from here — we usually can't just ask the hospital to send it again. Think of it as keeping the original receipt in case you ever need to dispute a charge.

Technical details
Stored as-is in cloud storage (e.g. Azure Data Lake) as JSON, alongside ingestion metadata: source system, timestamp, batch ID.
3

Organized into searchable tables

Raw files are slow to search. This step loads them into proper tables — like turning a folder of loose receipts into a spreadsheet — so questions get answered quickly later, and so many people can read and write at the same time without corrupting anything.

Technical details
Table formats like Iceberg or Delta Lake add version history and safe concurrent writes on top of plain files. Whether we actually need this at our scale is still open — covered in the tech-decisions chapter.
4

Medical vocabulary gets translated

Different hospitals describe the same disease differently — one writes "T2DM," another "Type 2 Diabetes Mellitus," another just uses a billing code. This step is a giant, pre-built medical dictionary that maps every version to one standard term, so "diabetes" always means the same thing no matter which hospital it came from. This is usually the hardest and most important part of the whole pipeline — more important than any storage technology.

Technical details
A source code (e.g. ICD-10 E11.9) is mapped to an OMOP standard concept (e.g. SNOMED 201826) using OHDSI's published vocabulary tables — this dictionary already exists, it isn't built from scratch.
5

Everything lands in one shared structure

Now every patient's data, regardless of which hospital it came from, sits in the same set of organized tables, using the same vocabulary. This is what makes it possible to ask "how many patients across everything we have are diabetic?" as one simple question instead of ten different ones per hospital.

Technical details
This shared structure is called the OMOP CDM. Core tables: PERSON, CONDITION_OCCURRENCE, MEASUREMENT, DRUG_EXPOSURE — all linked by person_id.
6

Common questions get pre-built

Some questions get asked over and over — "show me everything about our diabetic patients," for example. Instead of re-running a complicated multi-table search every time, we build a simplified, ready-made view for that specific question, so it's fast and easy for anyone to use.

Technical details
These are called data marts — e.g. a "Diabetes Mart" pre-joining PERSON, CONDITION_OCCURRENCE, MEASUREMENT, and DRUG_EXPOSURE.
7

A study's rules become a patient list

A clinical trial has written rules, like "age 40+, has diabetes, HbA1c above 7, on Metformin for the last year." This step turns those rules into a precise search and returns the exact list of patients who qualify, with a clear record of why each one was included. An AI can help read a lengthy protocol document and draft those rules — but it never touches the database directly. The actual matching is always done by regular, checkable code, so the result is the same and explainable every time you run it.

Technical details
The AI produces a structured specification, not raw SQL. That specification is validated, then compiled into SQL by deterministic code and run against OMOP — covered in the AI-architecture chapter.

1

Where the boundary sits

The hospital's EHR is the only box we don't own or control — everything to the right of it is our responsibility. The line between "their network" and "our cloud" is the single most important line on this diagram: it's where trust, security, and contracts all have to be figured out first.

Technical details
The hospital exposes a FHIR server / API at this boundary. Everything past it runs in our environment (e.g. Azure).
2

How we currently pull the data

Right now, getting data out means a script wakes up on a timer, asks the hospital's FHIR server "anything new?", and pulls it down — like refreshing your email inbox every hour instead of getting a notification the instant something arrives. That's worth remembering: it's a schedule-based design, not an instant, event-based one.

Technical details
Python scripts triggered by cron (Linux) or a similar Windows scheduled task, calling the FHIR REST API.
3

Where it lands in our cloud

The untouched copy and the organized, searchable version both live in our own cloud storage — this is the "our data" side of the boundary, fully under our control, backed up, and access-controlled.

Technical details
Raw JSON in blob storage (e.g. ADLS Gen2); organized tables in a lakehouse table format (e.g. Iceberg).
4

How it becomes OMOP

Two things happen side by side here: code reshapes the data into OMOP's table structure, while a separate reference dictionary translates each hospital's medical terms into one shared vocabulary. Both feed into the same result.

Technical details
ETL/ELT via Spark, dbt, and/or Python; vocabulary mapping backed by OHDSI's Athena vocabulary tables.
5

The OMOP warehouse

The fully organized, standardized data sits here, plus the ready-made views built for common questions. This is the "single source of truth" the rest of the system reads from.

Technical details
OMOP CDM tables (PERSON, CONDITION_OCCURRENCE, etc.) plus SQL views / data marts on top.
6

Cohort generation

An AI assistant reads a trial protocol and helps draft the matching rules; a separate, deterministic "cohort engine" actually runs those rules as SQL against the warehouse and produces the final patient list. The AI drafts, the engine decides.

Technical details
Covered in depth once we reach the AI-architecture chapter — including why the AI is never allowed to write or run SQL directly.
7

Running underneath everything

This isn't a step in the pipeline — it's the plumbing that keeps every other step running: something has to trigger jobs on schedule, something has to notice when a job fails, and something has to control who's allowed to touch what. Today that's cron jobs and a tool called NSSM (more on that below); whether that's the right long-term choice is a fair question for the next chapter.

Technical details
NSSM (Non-Sucking Service Manager) is a small Windows utility that wraps an ordinary script or program so Windows treats it like a background service — it restarts it if it crashes and starts it when the machine boots. It's a common way to keep a Python script "always running" on a Windows server without writing proper Windows service code. It works, but it's a single-machine, manually-managed approach with no built-in way to see job history, retry failures intelligently, or run on more than one server — the kind of thing we'll weigh against alternatives later.
STEP 03done

What could go wrong

Ten concrete ways the design in Chapter 02 could fail quietly, ranked by how much damage each would actually do — not by how technically interesting it is.

Why this comes before any tool choice None of this is about picking better software yet — it's about naming exactly what a good architecture needs to prevent. Every fix we design later traces back to one of these ten problems.

1. A "raw copy" that isn't actually protected

Critical

We said we'd keep a permanent, untouched copy of everything a hospital sends — but nothing yet stops it from being overwritten, and nothing records which version of our processing code turned a given raw record into a given OMOP row. If a mistake is found in the OMOP conversion six months from now, you need to reprocess exactly the affected data. Without this, you either reprocess everything and hope, or can't reprocess at all.

Why this matters technically
Needs write-protected (or at least delete-restricted) raw storage, a batch/run ID stamped on every raw file, and a traceable link from each OMOP row back to the exact raw file and pipeline version that produced it. This is the foundation of data lineage.

2. A patient can silently disappear from a cohort

Critical

If a hospital's diagnosis code has no match in the vocabulary dictionary, a simple ETL script typically just drops the row or leaves a field blank — with no error raised anywhere. A genuinely diabetic patient could be missing from a diabetes cohort not because they don't qualify, but because their hospital coded the diagnosis in a way the dictionary didn't recognize. Nobody would know unless they went looking.

Why this matters technically
Needs a required step that reports every source code with no standard-concept mapping. An "unmapped rate" should be a number on a dashboard, not a silent failure.

3. Running the same cohort twice could give two different answers

Critical

Generate a cohort today, generate the "same" one again in three months — if the vocabulary dictionary was updated, the ETL code was patched, or new data arrived, you could get a different patient list with no record of what changed or why. For a clinical trial, an unexplainable change in patient count is a serious problem, not a minor inconvenience.

Why this matters technically
Needs versioning on three axes, stamped on every cohort result: which vocabulary release was used, which pipeline code version ran, and a timestamped snapshot of the underlying data.

4. The whole pipeline is one Windows box away from stopping

High

Cron jobs and NSSM keep scripts running on a single machine. If that machine goes down, fills up its disk, or gets rebooted for a routine update, every scheduled job silently stops — and nobody finds out until a report is missing days later. There's also no shared view of which jobs ran, which failed, or why; someone has to log into that specific machine and dig through files.

Why this matters technically
No retry policy, no dependency graph (nothing stops the ETL job from starting before ingestion finishes), no central log or alert, and no way to run across more than one machine.

5. Data arrives on a schedule, not the moment it changes

High

A script that wakes up every hour or day and asks "anything new?" means data is always somewhat stale. If the hospital's FHIR server doesn't clearly support "only give me what changed since my last check," the script may re-download everything each run — wasting time and risking duplicate or inconsistent records if two runs overlap.

Why this matters technically
Needs confirmation the source supports incremental queries (e.g. a _lastUpdated search parameter), plus idempotent writes downstream so a re-pulled record doesn't create a duplicate.

6. Nothing stops bad data from reaching the warehouse everyone trusts

High

There's no checkpoint between "ETL just ran" and "this data is now in OMOP, ready to decide trial eligibility." A malformed date, an impossible lab value, or a duplicate record can flow straight through and quietly change who counts as eligible.

Why this matters technically
Needs validation gates: schema checks, null/referential-integrity checks, plausibility checks (an HbA1c of 400% is impossible), and row-count anomaly detection — ideally blocking promotion until checks pass.

7. Nobody has drawn an enforced line for what the AI can see

High

We said the AI drafts matching rules from the protocol but never touches patient data directly — the right instinct, but not yet an enforced rule anywhere. If someone later pastes real query results into a chat to debug something, or the assistant is given broader access for convenience, real patient data could reach a third-party AI service without anyone having decided that was okay.

Why this matters technically
Needs an explicit, enforced boundary: the AI's input is limited to protocol text and the concept vocabulary, never raw patient rows; its output is a structured spec, validated before anything executes.

8. One hospital's weird data can break everyone's pipeline

Medium

If every hospital's data flows through the same ETL script with no isolation, one hospital sending a slightly malformed record can halt processing for every other hospital's data too, instead of just failing for that one batch.

Why this matters technically
Needs per-source fault isolation, so a bad record or schema surprise from one source doesn't block another source's load.

9. Nothing is watching the numbers

Medium

If yesterday's ingestion brought in a million lab results and today only ten thousand arrived, would anyone notice — and how fast? The same goes for a cohort count suddenly dropping from 20,000 patients to 300. Right now, nothing compares "today" against "normal" and raises a flag.

Why this matters technically
Needs basic pipeline and cohort-result monitoring with thresholds and alerts — covered in the observability chapter.

10. Security has been assumed, not designed

Medium

Where do the credentials that let a script call the hospital's FHIR API actually live? Who can query OMOP directly instead of going through an approved view? Is data encrypted, and would anyone be alerted if someone accessed more patient records than their role should ever need? None of this has been decided yet — for healthcare data, it can't be bolted on right before launch.

Why this matters technically
Needs secrets management (not credentials sitting in a script file), encryption at rest and in transit, role-based access control, and audit logging of who accessed what.
Not a reason to panic This list is exactly why we're reviewing the design before writing code. Every one of these ten problems gets a specific answer when we choose tools (next chapter) and design the target architecture.
STEP 04done

Choosing the tools

One recommendation per decision, each one chosen specifically to close a gap from Chapter 03 — not a menu, and not the most impressive-sounding option.

Updated constraint: no paid Azure Everything below now runs on your own machine (or a free-tier VM) using free, open-source tools — this is much closer to what your RM actually described: Python scripts, Task Scheduler/cron, dbt, Iceberg, Spark if it's ever needed. Nothing here blocks moving to Azure later: every tool picked has a direct managed-Azure equivalent, so upgrading later means changing where something runs, not what it is or rewriting it.
The most optimal approach, in one paragraph Build the entire pipeline on free, boring, local tools first: Apache Iceberg for an immutable, versioned raw layer, Postgres for the OMOP warehouse (running in Docker on your own machine — Docker Desktop is free), dbt for every transformation and data-quality check, and Task Scheduler or cron directly for scheduling. That combination alone closes almost every gap from Chapter 03 without spending anything. The only paid piece is the AI layer itself (an API you call per request, typically pennies per run at this scale) — everything else is free until the day this needs to run reliably for people other than you, at which point each piece swaps to its managed-Azure equivalent one at a time.

Is Iceberg actually worth the extra moving part? Being fair to the other side of this: Iceberg adds a catalog to run and old snapshots that need periodic cleanup — a plain folder needs neither. That's a genuine cost for a solo project, not a free win just because it's open source. It earns that cost here specifically because it solves the single Critical gap from Chapter 03 — proving what the raw data looked like, and tracing every OMOP row back to an exact version — more solidly than any manual naming convention would, and because PyIceberg lets us get that without the much bigger cost (Spark, a JVM, cluster tuning) that normally comes attached to it.
Why this is a good place to start anyway, not just a budget compromise Building on your own machine forces short, fast feedback loops while you're still learning this domain — no cloud latency, no bill to worry about, nothing to tear down. And because every tool here (Iceberg, Postgres, dbt, Python, Task Scheduler) has a direct managed-Azure counterpart, none of this is throwaway work: the schema, the dbt models, and the pipeline logic all move to Azure later largely unchanged. You're not building a "toy" version and a "real" version — you're building the real one, just self-hosted for now.
When to actually move pieces to Azure
  • Someone other than you needs this to keep running when your laptop is off → move Postgres and the orchestration to the cloud first; everything else can follow gradually.
  • You're given real budget or a hospital partner requires cloud hosting for compliance reasons → that's the trigger to start the Azure migration, not data volume by itself.
  • Postgres feels slow under load (many concurrent analysts + cohort runs, whether local or cloud) → add a read replica first; consider Spark/Databricks only if that's genuinely not enough.
  • Scheduling gets tangled — dozens of steps, complex branching, hard to test locally → that's when Dagster or Airflow (still free, self-hostable) earns its place, independent of any Azure decision.

Glossary

Terms introduced so far. This grows as new chapters land.

EHR system
Electronic Health Record — the hospital's internal system of record (Epic, Cerner). Not directly queryable from outside.
HL7 v2 standard
Legacy healthcare messaging standard — pipe-delimited, event-driven (e.g. ORU^R01 for a lab result). Still runs most real-time ADT and lab feeds, but isn't queried directly for analytics.
FHIR standard
Fast Healthcare Interoperability Resources — REST API + JSON standard for exchanging one patient's clinical data in a predictable shape, regardless of source EHR.
Patient / Condition / Observation / MedicationStatement / Encounter FHIR resources
Core FHIR resource types: demographics, a diagnosis, a measured value (e.g. HbA1c), a reported medication, and the visit tying them together.
Bronze / silver / gold pattern
Common lakehouse layering: bronze = raw/immutable, silver = cleaned/conformed, gold = curated for consumption.
OMOP CDM standard
Observational Medical Outcomes Partnership Common Data Model — a normalized schema for population-level analytics, vocabulary-standardized so the same query works across data sources.
PERSON / CONDITION_OCCURRENCE / MEASUREMENT / DRUG_EXPOSURE OMOP tables
Core OMOP tables joined on person_id: patient identity, diagnoses, lab/vital values, and medication exposure periods.
Standard concept vocabulary
The OHDSI-designated canonical code for a clinical idea (e.g. SNOMED 201826 for Type 2 diabetes) — what a source code like ICD-10 E11.9 gets mapped to.
Concept set cohort logic
A standard concept plus all of its clinically valid descendant codes — e.g. "diabetes" expands to dozens of specific SNOMED codes.
